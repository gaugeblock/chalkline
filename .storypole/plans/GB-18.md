# GB-18: Configurable 9-Document Architecture Manager and AST-Grounded Documentation Generator

> **Status:** Planned / Specified  
> **Target Scope:** `chalkline-core`, `miter-engine`, `benchwork-core`, `benchwork/web`  
> **Key Architecture Decisions:** D1 (9-Document Taxonomy), D2 (Configurable `.gaugeblock/docs.toml`), D3 (Crate Ownership Boundaries)

---

## 1. Executive Summary & Vision

In modern AI-assisted systems engineering, project documentation frequently suffers from severe drift, semantic confusion, and misplaced concerns. Agents dump workflow rules into `CONTRIBUTING.md`, mix historical git commits into `ROADMAP.md`, duplicate type signatures into prose that diverges from actual code, or hallucinate CLI flags in `README.md`.

`GB-18` transforms repository documentation from a fragile afterthought into a deterministic, AST-grounded, configurable architecture managed by the `gaugeblock` suite:
1. **Canonical 9-Document Architecture:** An orthogonal, mutually exclusive separation of concerns across 9 essential markdown documents.
2. **Deterministic Grounding via `miter-engine`:** Verifying documentation claims against actual code ASTs, Clap argument definitions, Cargo workspace topologies, and Git histories.
3. **Convention over Configuration via `chalkline-core`:** Declarative `.gaugeblock/docs.toml` mapping with automatic fallbacks and brownfield section disentangling.
4. **Interactive Studio & Chat via `benchwork`:** A conversational doc setup wizard, section editor, and drift resolver natively embedded in Panel 1.

|  |       AGENTS.md        |  |       CHANGELOG.md       |  |          ARCHITECTURE.md           | |

### The 9-Row Taxonomy

| # | Document | Primary Audience | Core Question Answered | Canonical Boundary & Separation of Concerns |
|---|---|---|---|---|
| 1 | `README.md` | Public Users, Evaluators, Consumers | *What is this, why does it matter, and how do I run it in 30 seconds?* | Elevator pitch, high-level features, installation instructions, minimal quickstart CLI examples, badges, and links to deeper documentation. **MUST NOT** contain detailed developer build setup, internal crate topologies, or full API specs. |
| 2 | `CONTRIBUTING.md` | Human Contributors, Open-Source Devs | *How do I set up my local workstation, run tests, and open an acceptable PR?* | Local toolchain prerequisites (Rust, Node, pnpm), pre-commit hooks, code of conduct, PR etiquette, issue triage conventions, and environment variables. **MUST NOT** contain autonomous agent prompt directives or system boundaries. |
| 3 | `PRODUCT.md` | Product Managers, Designers, Users | *What user problems are we solving, and what are the user personas and jobs to be done?* | Product mission, target personas, user journeys, core user stories, high-level value propositions, and success metrics. **MUST NOT** contain technical AST schemas, crate hierarchies, or compiler flags. |
| 4 | `ARCHITECTURE.md` | Systems Engineers, Tech Leads | *How are the crates, processes, and runtime components wired together?* | Subsystem decomposition, crate graph topologies, IPC/RPC boundaries, data flow diagrams, thread/process lifecycle models, and network boundaries. **MUST NOT** contain ephemeral feature task lists or granular method-level signatures. |
| 5 | `SPEC.md` | Engineers, Test Authors, Verifiers | *What are the precise behavioral invariants, wire schemas, and error contracts?* | Formal state machines, protobuf/JSON schemas, algebraic data type contracts, preconditions, postconditions, and deterministic error codes. **MUST NOT** contain transient design rationales or discarded architectural explorations. |
| 6 | `DESIGN.md` | Implementers, Reviewers, Agents | *Why did we choose this technical approach over alternatives, and what are the trade-offs?* | Architectural Decision Records (ADRs), technical design proposals, rejected alternatives, trade-off matrices, benchmark experiments, and performance rationale. **MUST NOT** replace living behavioral contracts (`SPEC.md`). |
| 7 | `ROADMAP.md` | Stakeholders, Community, Contributors | *Where is this project going over the next quarters/milestones, and what is next?* | Major release themes, upcoming milestone epics, long-term research horizons, breaking change schedules, and deprecation timelines. **MUST NOT** contain retrospective changelog commit entries or completed bug notes. |
| 8 | `CHANGELOG.md` | Package Consumers, DevOps, SecOps | *What exactly changed between version X and version Y in production?* | Keep a Changelog (v1.1.0) format: Added, Changed, Deprecated, Removed, Fixed, Security per release tag, linked to commit hashes or PRs. **MUST NOT** contain speculative forward-looking roadmaps or aspirational designs. |
| 9 | `AGENTS.md` | LLM Agents, Meta-Harnesses, Automations | *What are the non-negotiable operational laws, tools, and execution loop for autonomous systems?* | File line count constraints, dogfooding rules, verification gates, commit standards, prompt conventions, toolchain rules, and autonomous error escalation laws. **MUST NOT** contain human contributor welcome notes or PR templates. |

## 3. Boundary Disambiguation Tables

### Why `CONTRIBUTING.md` != `AGENTS.md`

| Dimension | `CONTRIBUTING.md` | `AGENTS.md` |
|---|---|---|
| **Audience** | Human developers, community open-source contributors | Autonomous AI agents, subagents, prompt compilers |
| **Tone & Style** | Welcoming, polite, instructional, descriptive | Imperative, legalistic, strict, non-negotiable |
| **Tooling Guidance** | Recommended IDE plugins, code style guidelines, PR templates | Strict CLI execution policies, tool schema bindings, forbidden flags |
| **Constraints** | Encouraged practices (e.g. "please run tests before pushing") | Hard compiler lints, line-of-code ceilings (<=250 LOC), zero-unwrap rules |
| **Execution Loop** | Manual feature branching, issue assignment, code review steps | Claim-Lease-Verify DAG workflow, heartbeat protocols, Storypole verification |

### Why `CHANGELOG.md` != `ROADMAP.md` != `DESIGN.md`

| Dimension | `CHANGELOG.md` | `ROADMAP.md` | `DESIGN.md` |
|---|---|---|---|
| **Time Horizon** | Historical (Past Releases) | Future (Planned Milestones) | Present / Living (Architecture & Rationale) |
| **Truth Anchor** | Immutable Git tags & released binaries | Mutable strategic goals & target horizons | Validated technical decisions & active tradeoffs |
| **Source of Truth** | Conventional Commits (`git log <tag>..HEAD`) | Milestone epics, product strategy, RFCs | ADRs, system design proposals, spike results |
| **Mutability** | Append-only per released version | Continuously reprioritized and refined | Updated when architectural patterns mutate |

## 4. Configuration Schema (`.gaugeblock/docs.toml`)

Projects define their documentation layout and enforcement policies via `.gaugeblock/docs.toml`. If omitted, standard conventions apply.

```toml
# .gaugeblock/docs.toml — Gaugeblock Documentation Architecture Configuration

[docs]
# Convention-over-configuration: defaults to root file, or docs/<name>.md
readme = { path = "README.md", required = true }
contributing = { path = "CONTRIBUTING.md", required = true }
product = { path = "docs/PRODUCT.md", required = false }
architecture = { path = "ARCHITECTURE.md", required = true }
spec = { path = "SPEC.md", required = true }
design = { path = "DESIGN.md", required = false }
roadmap = { path = "ROADMAP.md", required = false }
changelog = { path = "CHANGELOG.md", required = true }
agents = { path = "AGENTS.md", required = true }

[docs.policies]
# Enforce that all public structs and functions in Rust/TS are documented
enforce_public_type_contracts = true

# Enforce that ARCHITECTURE.md contains all Cargo workspace members
enforce_crate_topology = true

# Enforce that no doc file exceeds 500 lines without splitting
enforce_file_loc_limits = true

# Audit README.md CLI flags against Clap CLI definitions
enforce_readme_cli_flags = true

# Audit CHANGELOG.md Unreleased section against Git commits since last tag
enforce_changelog_unreleased = true

# Audit CONTRIBUTING.md against rust-toolchain.toml and package.json engines
enforce_contributing_toolchains = true
```

## 5. AST & Git Cross-Check Engine

Documentation verification must be deterministic. The cross-checking engine performs static verification:

1. **`README.md` CLI Audit:**
   - Uses `miter-engine` to parse Clap / CLI definition trees.
   - Extracts all subcommands, arguments, and flags from code AST.
   - Verifies that every markdown code block demonstrating a CLI invocation uses valid flags and existing subcommands.
   - Checks that all relative repository links (`[file](crates/...)`) point to existing files on disk.

2. **`CHANGELOG.md` Commit Audit:**
   - Inspects `git describe --tags --abbrev=0` to identify the most recent release tag.
   - Parses `git log <last-tag>..HEAD --oneline` looking for Conventional Commits.
   - Flags unreleased `feat` or `fix` commits that are absent from the `## [Unreleased]` section of `CHANGELOG.md`.

3. **`CONTRIBUTING.md` Toolchain Audit:**
   - Reads `rust-toolchain.toml` (channel, components, targets) and `package.json` (`engines.node`, `packageManager`).
   - Verifies that `CONTRIBUTING.md` mentions the exact matching minimum versions, preventing contributor onboarding friction.

4. **`SPEC.md` Public Type Contract Audit:**
   - Uses `miter-engine` AST index to inspect public traits, structs, enums, and interfaces.
   - Cross-checks type names mentioned in code fences in `SPEC.md` against the index; flags renamed or deleted types.

5. **`ARCHITECTURE.md` Workspace Topology Audit:**
   - Reads root `Cargo.toml` (`workspace.members`) or root `pnpm-workspace.yaml`.
   - Verifies that every sub-crate / package has a corresponding entry or description in `ARCHITECTURE.md`.

## 6. Brownfield Disentangler (`DocMigrationPlan`)

Existing codebases often have a single bloated `README.md` or `CONTRIBUTING.md` containing a messy amalgamation of agent rules, changelogs, architecture notes, and specs.

The Brownfield Disentangler parses existing documents and automatically classifies sections:
1. **Markdown AST Parser:** Breaks down files into section blocks based on H1 (`#`) and H2 (`##`) headers.
2. **Deterministic Classifier:**
   - Sections containing "Autonomous Agent", "File Limit", "Verification Matrix" -> `AGENTS.md`
   - Sections containing "Keep a Changelog", "v0.1.0", "Release Notes" -> `CHANGELOG.md`
   - Sections containing "Prerequisites", "Setting up local dev", "Opening a PR" -> `CONTRIBUTING.md`
   - Sections containing "Subsystems", "Crates", "Data Flow" -> `ARCHITECTURE.md`
   - Sections containing "ADR", "Decision Log", "Tradeoffs" -> `DESIGN.md`
3. **Migration Plan Proposal (`DocMigrationPlan`):**
   - Proposes non-destructive git diffs: cleanly extracting the classified text blocks into the target files defined in `.gaugeblock/docs.toml`.
   - Preserves all text and links with zero information loss.

## 7. UI Studio & Chat Workflows (Benchwork Panel 1)

Benchwork Panel 1 provides a visual and conversational experience for managing the 9-Document Architecture:

1. **Zero-Doc / Partial-Doc Wizard:**
   - Scans the active repository for the 9 canonical documents.
   - Displays a clean visual checklist with badges: `Present`, `Missing`, `Drifted`.
   - Offers a one-click "Scaffold Missing Docs" action populated with AST-grounded templates.

2. **Doc Settings Gear:**
   - Interactive modal to customize `.gaugeblock/docs.toml`.
   - Allows users to remap paths (e.g. `PRODUCT.md` -> `docs/product_vision.md`), toggle required statuses, and toggle individual verification policies.

3. **Conversational Documentation Chat:**
   - Embedded chat interface in Panel 1 powered by `benchwork` and `chalkline`.
   - Users can prompt: *"Audit my documentation against current code"*, *"Extract agent rules from CONTRIBUTING.md into AGENTS.md"*, or *"Generate SPEC.md based on public crate traits"*.
   - Surfaces interactive diff proposals with side-by-side preview and one-click apply.
